# Assignment 1 — Lakebase-Powered AI Ticket Support App

Day 1 boot camp homework: a **Databricks App** (Flask) backed by **Lakebase**
(Databricks-managed Postgres). Users view, create, and message support tickets
from a browser UI, and change ticket status — all reading and writing through
Lakebase. Foundation for the context-engineering and AI-agent work later in the
boot camp.

## Architecture

```
Browser (UI)                          Databricks Secrets
    │  HTTP                                 │
    ▼                                       │  (secret fetch on cold start)
┌────────────────────┐                      ▼
│  Flask app (app.py)│  ── lakebase.py ──► LAKEBASE_URL
│  templates/        │      psycopg2                │
│    index.html      │      RealDictCursor          │  postgres://
└────────────────────┘                              ▼
        ▲                              ┌────────────────────────┐
        │   fetch() JSON               │  Lakebase (Postgres)   │
        └──────────────────────────────┤  tickets               │
                                       │  ticket_messages       │
                                       │  (FK, ON DELETE CASCADE)│
                                       └────────────────────────┘
```

`lakebase.py` fetches the Postgres connection URL from a Databricks **secret**
(`database/lakebase-url`) at runtime and base64-decodes it — the live credential
never lives in the app's environment. Helper API: `run_query` (read),
`run_write` (write), `get_connection` (a psycopg2 connection for
`INSERT ... RETURNING`).

## What's implemented

| Feature | Status |
|---|---|
| View all tickets | ✅ `GET /tickets` + list panel in UI |
| Select a ticket and view its messages | ✅ `GET /tickets/<id>` + detail pane with thread |
| Create a new ticket | ✅ `POST /tickets` + `+ New` modal in UI |
| Add a message to a ticket | ✅ `POST /tickets/<id>/messages` + compose box in UI |
| Update a ticket's status | ✅ `PATCH /tickets/<id>/status` + status dropdown in UI |
| Reads/writes hit Lakebase (no hard-coded data) | ✅ every route talks to Postgres via `lakebase.py` |
| Schema: 2 related tables with FK | ✅ `tickets` ← `ticket_messages` (FK, `ON DELETE CASCADE`) |
| Seed: 3+ tickets, 2+ msgs each, 2+ statuses | ✅ 3 tickets, 2–3 messages each, all 3 statuses |
| Deployable as a Databricks App | ✅ `app.yaml` + secret-pointer env vars |

## API

| Method & path | Purpose |
|---|---|
| `GET /` | Ticketing UI (renders `templates/index.html`) |
| `GET /healthz` | Liveness (no DB) |
| `GET /tickets` | List tickets, newest first |
| `POST /tickets` | Create a ticket — body `{title, status?, created_by?}` |
| `GET /tickets/<ticket_id>` | A ticket plus its message thread |
| `POST /tickets/<ticket_id>/messages` | Add a message — body `{message_text, author?}` |
| `PATCH /tickets/<ticket_id>/status` | Update status — body `{status}` (`open`\|`in_progress`\|`resolved`) |

`created_by` / `author` default to the logged-in user's email (pulled from the
`X-Forwarded-Email` header that Databricks Apps inject).

## Schema

Two tables, one foreign key. Postgres ENUM for status, UUID PKs generated by
the DB (`gen_random_uuid()`), `timestamptz` defaults. Idempotent DDL — safe to
re-run `init_db.py`.

```
tickets
  ticket_id   UUID PK (default gen_random_uuid())
  title       VARCHAR(255) NOT NULL
  status      issue_status NOT NULL DEFAULT 'open'
              ENUM('open','in_progress','resolved')
  created_by  TEXT
  created_at  TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP

ticket_messages
  message_id    UUID PK (default gen_random_uuid())
  ticket_id     UUID NOT NULL  FK → tickets.ticket_id  ON DELETE CASCADE
  message_text  TEXT NOT NULL
  author        TEXT
  created_at    TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
```

See [sql/schema.sql](sql/schema.sql) and [sql/seed.sql](sql/seed.sql).

## Project structure

| Path | What it is |
|---|---|
| `app.py` | Flask app: 5 ticket routes + `/` UI + `/healthz` |
| `lakebase.py` | Secret-backed connection helper (`run_query`/`run_write`/`get_connection`) |
| `templates/index.html` | Single-page UI (vanilla JS + fetch), dark/light theme, no external assets |

| `app.yaml` | Databricks Apps deploy config (`python app.py` + secret-pointer env vars) |
| `requirements.txt` | Python dependencies |

## Local development

The app resolves its DB URL from a Databricks secret, so local runs need
Databricks auth **and** the secret to exist.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 1. Authenticate to Databricks (a CLI profile or DATABRICKS_HOST/_TOKEN env vars)

# 2. Store the Lakebase URL as a secret (interactive, hidden input — safer than export)
python setup_secrets.py
#    when prompted, paste:
#    postgresql://<role>:<password>@<host>:5432/databricks_postgres?sslmode=require

# 3. Apply schema + seed to Lakebase (idempotent)
python init_db.py

# 4. Run the app
python app.py         # http://localhost:8000/
```

Open http://localhost:8000/ — three seeded tickets should render. Click one to
see its thread, use **+ New** to create a ticket, the status dropdown to change
state, and the compose box to add a message.

`GET /healthz` works without the database; the ticket routes need the schema +
seed applied.

### About the Lakebase URL

- Never `export LAKEBASE_URL='...'` on zsh without single-quotes — the `?` in
  the URL is a glob character and zsh will error out with `no matches found`.
- The interactive `setup_secrets.py` prompt avoids all shell interpretation
  (via `getpass`), so paste-as-hidden-input is the recommended path.
- Anything pasted into a chat channel, log, or shell history is compromised.
  Rotate the role's password if in doubt.

## Deploy to Databricks Apps

1. Provision Lakebase — **Compute → Database Instances → Create** (Autoscaling
   project). Create a native Postgres role with a static password, grab the
   connection URL.
2. Store the secret — `python setup_secrets.py` (once, from anywhere with
   Databricks auth).
3. Create the App — **Compute → Apps → Create App**. Point it at this repo
   (Git integration or uploaded artifact). Databricks reads `app.yaml`, which
   tells it to run `python app.py` and injects `LAKEBASE_SECRET_SCOPE` /
   `LAKEBASE_SECRET_KEY` so the app resolves the URL from the secret at
   runtime.
4. Deploy — from the repo root:

    ```bash
    databricks apps deploy <app-name> --source-code-path .
    ```

The App URL comes back in the CLI output and appears in the Databricks UI
under the App's detail page.
